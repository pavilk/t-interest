# Tinterest — бэкенд

Студенческий проект ФИИТ УрФУ (X2609-413, команда «риил»). Заказчик — Т-Банк.

Это репозиторий **бэкенда**. Веб (React + TypeScript) живёт в отдельном репозитории и общается с бэком только через HTTP API и WebSocket. Контракт — OpenAPI-схема FastAPI (`/openapi.json`); фронт генерирует из неё типы.

## Цель продукта

Внутреннее приложение для сотрудников Т-Банка и Центров разработки. Оно помогает находить коллег по интересам, общаться не только на рабочие темы, заводить и поддерживать знакомства.

Приложение строго внутреннее: данные сотрудников не должны уходить за пределы компании (см. «Безопасность и данные»).

**Критерии приёмки:** пользователь регистрируется, заполняет анкету, находит человека или группу по интересам и продолжает общение в чате.

## Функциональность и приоритеты

Порядок работы (решено на синке):

1. **Анкета.** Регистрация → оформление профиля → анкета (обязательна при первом входе). Вопросы и интересы хранятся в БД, а не в коде.
2. **Основная страница:** чаты, рекомендации (людей и групп), поиск.
3. **Группы по интересам.** Есть группы по существующим интересам. Любой пользователь может создать группу по новому интересу, если такой ещё нет, но она появляется только после модерации.

Матчинг: 1:1 (человек ↔ человек) и группы. Учитываются ответы анкеты и дополнительные признаки (локация / офис).

Чат: личные и групповые чаты в реальном времени, отдельная вкладка «как в Telegram».

Не в MVP: фильтры, ивенты групп, уведомления сверх счётчика непрочитанных.

## Слои

Зависимости идут строго в одну сторону: `api → services → repositories → models`.

- **api**: только HTTP/WS. Никакой бизнес-логики и прямых запросов к БД.
- **services**: бизнес-правила. Работают с репозиториями, возвращают доменные данные или схемы.
- **repositories**: один репозиторий на агрегат — `UserRepository`, `SurveyRepository` (вопросы, варианты, ответы), `InterestRepository` (интересы, интересы пользователя), `MatchRepository`, `GroupRepository`, `ChatRepository` (чаты, участники, сообщения). Принимают `AsyncSession`, не делают `commit`.
- **Транзакции**: HTTP — одна сессия на запрос через `Depends(get_session)`; `commit` делает только эта зависимость после успешного ответа, при исключении — `rollback`. Сервисы и репозитории не коммитят.
- **WebSocket**: соединение живёт долго, поэтому сессия создаётся **на каждое входящее сообщение**, а не на соединение.
- **Тесты**: сервисы — с фейковыми репозиториями; репозитории — на тестовой PostgreSQL.

## Основные сущности

Все `created_at` — `timestamptz` в UTC.

- **User**: id, email (unique), password_hash, name, about, office_id, role (user / moderator / admin), survey_completed, created_at.
- **Office**: id, city, name. Справочник, чтобы локация сравнивалась без опечаток.
- **Interest**: id, name, parent_id? Дерево из двух уровней: направление (спорт, искусство, отдых…) → поднаправление (волейбол, театр, бар…). Для матчинга используются поднаправления.
- **UserInterest**: user_id, interest_id. PK (user_id, interest_id).
- **Question**: id, text, type (single / multi / text), order, is_active. Вопросы не удаляются, только деактивируются.
- **AnswerOption**: id, question_id, text, interest_id? Выбор варианта со ссылкой на интерес даёт пользователю этот интерес.
- **UserAnswer**: id, user_id, question_id, option_id?, text_value?. Ровно одно из двух заполнено (CHECK). UNIQUE (user_id, question_id, option_id). Свободный ответ («Другое») показывается в профиле, в скоринге не участвует.
- **Match**: id, user_a_id, user_b_id, score, a_status, b_status (pending / accepted / declined), created_at. Всегда `user_a_id < user_b_id`, UNIQUE (user_a_id, user_b_id). Пара взаимная, когда оба статуса `accepted`.
- **Group**: id, name, description, interest_id, created_by, status (pending / approved / rejected), created_at. Пользователям видны только `approved`.
- **GroupMember**: group_id, user_id, role (owner / member). PK (group_id, user_id).
- **Chat**: id, type (direct / group), group_id?. Личный чат между двумя людьми только один.
- **ChatMember**: chat_id, user_id, last_read_message_id?. PK (chat_id, user_id).
- **Message**: id, chat_id, sender_id, text, created_at.

Если схема в коде расходится с этим списком, обнови этот раздел.

## Матчинг (первая версия)

- Простой и объяснимый скоринг: Jaccard по интересам пользователя (поднаправления) плюс бонус за совпадение офиса/города.
- Скоринг лежит в `services/matching.py` как чистые функции без БД и покрыт unit-тестами. Данные для него загружаются через репозитории.
- Не показывать пользователю его самого, уже отклонённые пары и заблокированных.
- Рекомендации групп: одобренные группы по интересам пользователя, в которых он ещё не состоит.

## Группы и модерация

- Создать группу может любой пользователь, если для этого интереса ещё нет одобренной группы. Новый интерес создаётся вместе с заявкой.
- Новая группа получает `status = pending` и не видна никому, кроме автора и модераторов.
- Модератор (`role = moderator / admin`) одобряет или отклоняет. После одобрения создаётся групповой чат, автор становится `owner`.

## Чат (реалтайм)

- JWT для WS передаётся при подключении (браузер не умеет ставить заголовки для WS). Способ выбирается вместе с вебом.
- При каждом сообщении проверяется членство отправителя в чате.
- Рассылка через менеджер соединений в памяти процесса, поэтому бэкенд запускается **одним воркером**. Если понадобится масштабирование — Postgres `LISTEN/NOTIFY`, без внешних брокеров.

## Безопасность и данные

- Никаких внешних сервисов, которые получают данные пользователей: никакой сторонней аналитики или внешних AI API.
- Всё self-hosted: работает в Docker в контуре компании.
- Пароли хэшируются (argon2 / bcrypt), авторизация через JWT. Секреты только в `.env`, а `.env` в `.gitignore`. Пример — в `.env.example`.
- Регистрация разрешена только для email из доменов, указанных в конфиге.
- Каждый эндпоинт, кроме регистрации и входа, требует авторизации. Эндпоинты модерации — только для moderator / admin.
- Не логировать персональные данные и содержимое сообщений.
- Сиды и тестовые данные — только вымышленные.
